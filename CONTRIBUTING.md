### ☠︎ 01 — BEFORE YOU BEGIN

Contributing is more than adding code.

It means understanding the structure, respecting the project's direction, and bringing something meaningful to its evolution.

You don't need to know everything.

You need to be willing to learn, investigate, and understand what you're changing.

### ⛓ 02 — CONTRIBUTION PRINCIPLES

- **Understand before changing:** Explore the existing implementation before modifying it.
- **Keep things organized:** Write readable, maintainable, and consistent code.
- **Experiment responsibly:** Test your changes before submitting them.
- **Respect the structure:** Avoid unnecessary modifications unrelated to your contribution.
- **Explain your work:** Make it clear what changed and why.
- **Learn from failures:** Bugs are part of development, not something to hide.

### ⚙︎ 03 — HOW TO CONTRIBUTE

**01. Fork the repository**

Create your own copy of ULQUIORRA-BOT.

**02. Clone your fork**

```bash
git clone YOUR_FORK_URL
cd ULQUIORRA-BOT
```

**03. Create a branch**

```bash
git checkout -b feature/your-feature
```

**04. Make your changes**

Implement your idea, fix a bug, or improve an existing feature.

**05. Test your modifications**

Check for unexpected behavior, errors, and compatibility issues.

**06. Commit your work**

```bash
git add .
git commit -m "feat: describe your changes"
```

**07. Push your branch**

```bash
git push origin feature/your-feature
```

**08. Open a Pull Request**

Describe your contribution, explain the changes, and provide relevant details.

### 🩸 04 — COMMIT CONVENTION

Whenever possible, use clear commit prefixes:

| Prefix | Purpose |
|:---|:---|
| `feat:` | New functionality |
| `fix:` | Bug fixes |
| `refactor:` | Code restructuring |
| `docs:` | Documentation changes |
| `style:` | Formatting and visual adjustments |
| `perf:` | Performance improvements |
| `test:` | Tests and validation |

Example:

```bash
git commit -m "feat: add sticker pack generator"
```

### 𖣘 05 — WHAT SHOULD BE AVOIDED

- Unnecessary code duplication.
- Hardcoded credentials, tokens, or personal information.
- Unexplained changes to existing functionality.
- Unrelated modifications bundled into one Pull Request.
- Malicious behavior, destructive payloads, or abusive automation.
- Dependencies added without a clear reason.

### ⛧ 06 — PULL REQUEST CHECKLIST

Before submitting your contribution:

- [ ] The changes have been tested.
- [ ] The code follows the existing project structure.
- [ ] No credentials or sensitive information were exposed.
- [ ] The Pull Request explains what was changed.
- [ ] Unrelated files were left untouched.

### ☣︎ 07 — THE FINAL PROTOCOL

> "Not everything that runs is alive. Not everything that breaks is a failure."

Don't contribute just to add another line of code.

Contribute because you understood something, discovered something, or found a better way to build it.

Question the structure. Understand the system. Improve what you can.

**NO BLIND FOLLOWING. NO EMPTY CONTRIBUTIONS. JUST EVOLUTION.**
